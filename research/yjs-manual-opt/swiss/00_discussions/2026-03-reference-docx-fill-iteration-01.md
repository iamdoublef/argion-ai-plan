# 2026-03 参考 Word 填充路线迭代研究 01

## 这轮先给结论

如果目标是：

- 和参考版样式一致度达到 90% 以上
- 内容不是写死，而是填充进去
- 仍然满足 Swiss 生产要求

当前最有希望、而且已经在仓库里跑出原型的路线，不是继续强化 `docx` npm 程序式生成，而是：

**直接拿参考 `.docx` 做真母版，只改内容节点，尽量不碰版式骨架。**

这条线已经有本地 PoC：

- 脚本：`research/yjs-manual-opt/swiss/tools/assemble-v22-chinese-demo.py`
- 输入：`research/yjs-manual-opt/_inbox/V22 Vacuum Sealer-User Manual-20260206.docx`
- 输出：`research/yjs-manual-opt/swiss/output/v22-wevac-cn-demo-iter.docx`

## 本地验证结果

2026-03-22 本地实跑 `assemble-v22-chinese-demo.py`，结果如下：

- Cover: `5/5`
- TOC: `27/27`
- 一级标题 H1: `9/9`
- 二级标题 H2: `17/17`
- 正文段落: `191`
- 表格单元格: `46`
- 总替换量: `295`
- 未命中: `3`

未命中的 3 处都不是正文失败，而是图号类段落：

- `Figure 2Figure 2`
- `Figure 4Figure 4`
- `Figure 5Figure 5`

## 为什么这条线目前最接近目标

### 1. 它本质上保留了参考件的版式资产

该脚本不是“重新画一份 Word”，而是：

1. 解包参考 `.docx`
2. 直接改 `word/document.xml` 里的文本节点
3. 保留图片、表格、章节结构、段落样式
4. 回写并重新打包

这意味着：

- 参考版已有的封面、目录、表格、分页、图片布局天然被继承
- 样式一致度不是靠程序“模仿”，而是靠“沿用原件”

### 2. 当前输出对源文件的改动面非常小

本地对比 source / output zip 内容后，发现真正发生内容差异的核心文件只有：

- `word/document.xml`
- `word/styles.xml`

这说明这版 PoC 的逻辑本质上还是“借原文档的壳，换里面的字”，不是把整份 Word 重建一遍。

### 3. 这比当前 `export-docx.js` 更像你要的方向

`export-docx.js` 的路线是：

- 用 `docx` npm 从零生成 Word
- 程序负责排版
- Word 只是输出容器

这条线天花板很明显，仓库里之前的研究也已经下过结论：

- 它适合“可编辑但体面”的 Word
- 不适合“高度接近参考件”的 Word

而 `assemble-v22-chinese-demo.py` 的路线正好相反：

- 参考件负责版式
- 程序负责换字、换少量字体策略

这更符合“样式还原优先”的目标。

## 但它现在还不是正式生产链

这版 PoC 已经证明方向对，但离正式生产还有 4 个硬问题。

### 1. 它现在还是“全文映射替换”，不是结构化填充

当前依赖：

- `v22-cn-translations.json`

本质是英文段落 -> 中文段落的映射替换，不是直接吃 Swiss 的：

- `product.json`
- `images.json`
- `content/source/chapters/*.json`
- `i18n/compiled/<locale>.json`

所以它更像“保版式翻译器”，还不是“正式生成器”。

### 2. 它依赖参考件结构稳定

当前匹配方式大量依赖：

- 段落原文
- 段落样式号
- 表格单元格原文

只要参考件换一版，段落拆分、样式号、目录字段、图注结构一变，匹配规则就要跟着修。

### 3. 图号和少量特殊块还没完全吃透

未命中已经暴露一个事实：

- 图号、混合 run、图文复合段落，比普通正文更脆

这类块如果要进正式生产，必须补独立规则，不能靠正文替换顺手带过去。

### 4. 还没有做正式视觉验收

当前环境没有现成的 `soffice` / `pdftoppm`，这轮只能从机制和 XML 改动面判断。

结论可以下到：

- **方向成立**
- **PoC 很强**

但还不能在没有渲染验收的情况下，正式宣布“100% 过版”。

## 这轮对“90% 还原”的判断

基于当前机制和本地结果，我的判断是：

### 能打到 90% 以上的路线优先级

1. **最高优先级：参考 DOCX 直接填充 / 替换**
2. 第二优先级：`docxtpl` / `poi-tl` 真母版注入
3. 不建议继续押注：`docx` npm 程序式生成
4. 不建议：HTML -> DOCX 转换

原因很直接：

- 要 90% 样式还原，最稳的不是“重画得像”，而是“直接保留原骨架”
- 真母版注入也能接近，但前提是母版本身得先在 Word 里设计好
- 纯程序式生成永远在追样式，不是在继承样式

## 接下来该怎么迭代

### 路线 A：把现有 PoC 升级成“参考件驱动生成器”

这是当前最短路径。

要补 5 件事：

1. 把 V22 demo 的替换逻辑抽象成通用引擎
2. 从“原文映射替换”升级成“Swiss JSON -> 参考件锚点填充”
3. 给图号、图注、目录字段、页眉页脚单独建规则
4. 给每个产品线维护“参考批准版 docx”
5. 增加 DOCX 渲染验收流程

适用前提：

- 你手上确实有高质量参考 Word
- 参考件本身就是想保住的样式基线

### 路线 B：参考件重做为真模板，再上 docxtpl / poi-tl

这是更标准化的中期路线。

做法是：

1. 在 Word 里把参考件整理成可注入模板
2. 用占位符、循环块、表格模板承接结构化内容
3. 由 `docxtpl` 或 `poi-tl` 注入 Swiss JSON

优点：

- 生产链更规范
- 更适合批量化和多产品复用

缺点：

- 模板工程量比路线 A 大
- 前期需要人工把参考件“模板化”

## 当前建议

如果你现在的目标是尽快打出一版“看起来几乎就是参考件，只是内容换成目标内容”的成品，建议顺序是：

1. 先沿 `assemble-v22-chinese-demo.py` 这条线继续做
2. 用一份批准版 Word 做基底，先证明 90% 样式还原
3. 再把 PoC 清洗成正式模板注入链

也就是说：

**先赢样式，再整理工程。**

这比一开始就追求“完美通用架构”，更符合当前阶段目标。
